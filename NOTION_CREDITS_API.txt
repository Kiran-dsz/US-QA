Helper API: Set Version Tag\n```plain text\nPOST /mem-app/v4/credits/test/version-tag\n```\n### What it does\nIt writes the same Membership-side 4.0 state used by the production Kafka/user-service path and immediately runs the normal Preview eligibility evaluator.\nIt does not bind a device and does not force Preview to become active.\n### When to use it\nUse this helper to:\n- test `pending_4_0` and `pending_device`;\n- test both 4.0/device signal orders;\n- remove the 4.0 signal and verify eligibility changes;\n- test duplicate or stale Version Tag events without waiting for the upstream Kafka topic.\nDo not use it to prove the real Version Tag producer, broker, or consumer works. Keep a separate Kafka smoke test for that transport.\n### Request parameters\n<table header-row=\"true\">\n<tr>\n<td>Field</td>\n<td>Required</td>\n<td>Meaning</td>\n</tr>\n<tr>\n<td>`is_4_0_user`</td>\n<td>Yes</td>\n<td>`true` sets the signal; `false` removes it</td>\n</tr>\n<tr>\n<td>`event_id`</td>\n<td>No</td>\n<td>Explicit event identity for duplicate-event tests</td>\n</tr>\n<tr>\n<td>`version`</td>\n<td>No</td>\n<td>Explicit ordering version for stale-event tests</td>\n</tr>\n<tr>\n<td>`occurred_at`</td>\n<td>No</td>\n<td>RFC3339 event time for ordering tests</td>\n</tr>\n</table>\nUser, workspace, and member identity come from the Workspace Token. For normal QA and automation, send only `is_4_0_user`; the service generates the optional ordering fields safely.\n### Set the user as 4.0\n```bash\ncurl -sS -X POST \\\n  \"$APP_URL/mem-app/v4/credits/test/version-tag\" \\\n  -H \"Authorization: Bearer$WT\" \\\n  -H \"X-Test-Run-ID:$RUN_ID\" \\\n  -H \"Content-Type: application/json\" \\\n  -d \"{\n\\\"is_4_0_user\\\": true\n  }\" | jq\n```\nTypical response before device binding:\n```json\n{\n  \"status\": 0,\n  \"msg\": \"success\",\n  \"data\": {\n    \"applied\": true,\n    \"event_id\": \"dev_test_...\",\n    \"version\": 4,\n    \"skipped_reason\": null,\n    \"activation_status\": \"pending_device\"\n  }\n}\n```\nDo not provide `event_id`, `version`, or `occurred_at` in normal tests. The server generates a unique event ID and the next valid version.\n### How to read the result\n<table header-row=\"true\">\n<tr>\n<td>Field</td>\n<td>Meaning</td>\n</tr>\n<tr>\n<td>`applied=true`</td>\n<td>The signal changed Membership state and the evaluator ran</td>\n</tr>\n<tr>\n<td>`applied=false`</td>\n<td>A valid no-op, such as duplicate, stale, or Preview disabled</td>\n</tr>\n<tr>\n<td>`event_id` / `version`</td>\n<td>Actual generated or supplied ordering identity</td>\n</tr>\n<tr>\n<td>`skipped_reason`</td>\n<td>Why a valid event did not change state</td>\n</tr>\n<tr>\n<td>`activation_status`</td>\n<td>Result after evaluating both 4.0 and authoritative device state</td>\n</tr>\n</table>\nCommon `activation_status` values:\n<table header-row=\"true\">\n<tr>\n<td>Status</td>\n<td>Meaning</td>\n</tr>\n<tr>\n<td>`pending_device`</td>\n<td>4.0 is true, but no authoritative bound device was found</td>\n</tr>\n<tr>\n<td>`pending_4_0`</td>\n<td>Device condition exists, but 4.0 is not true</td>\n</tr>\n<tr>\n<td>`active` / `already_active`</td>\n<td>Both conditions are satisfied</td>\n</tr>\n<tr>\n<td>`provisioning`</td>\n<td>Eligibility passed and asynchronous grant setup is converging</td>\n</tr>\n</table>\n### Remove the 4.0 signal\n```bash\ncurl -sS -X POST \\\n  \"$APP_URL/mem-app/v4/credits/test/version-tag\" \\\n  -H \"Authorization: Bearer$WT\" \\\n  -H \"X-Test-Run-ID:$RUN_ID\" \\\n  -H \"Content-Type: application/json\" \\\n  -d \"{\n\\\"is_4_0_user\\\": false\n  }\" | jq\n```\n### Test duplicate or stale events\nFor ordering-specific tests only, explicitly send `event_id`, `version`, and `occurred_at`. A valid no-op still returns HTTP `200`, with:\n```plain text\napplied=false\nskipped_reason=duplicate_event | stale_version | preview_disabled\n```\n---\n## 3. The Application fills in the authenticated workspace, member, region, and subject before forwarding it.\nThe helper skips only Kafka transport. It still runs:\n```plain text\nschema validation\n→ authorization validation\n→ task claim and idempotency\n→ Metronome ingest\n→ local History rating\n→ delayed balance refresh\n→ change-gated credits_updated notification\n```\n### When to use it\nUse this helper to:\n- charge Agent, AI Note, TTS, ASR, or mixed task usage without a Kafka producer;\n- test Before authorization settlement;\n- test one-task/multiple-line aggregation;\n- test Usage idempotency and invalid payload handling;\n- drive balance into `low` or `exhausted` for Overview and Reset testing;\n- create History records and trigger the normal delayed balance refresh.\nIt does not test Kafka IAM, topic metadata, consumer group, offset commit, retry, or DLQ.\n### CloudEvent parameters\n<table header-row=\"true\">\n<tr>\n<td>Field</td>\n<td>Required</td>\n<td>Meaning</td>\n</tr>\n<tr>\n<td>`specversion`</td>\n<td>Yes</td>\n<td>Must be `\"1.0\"`</td>\n</tr>\n<tr>\n<td>`id`</td>\n<td>Yes</td>\n<td>Unique CloudEvent ID; Helper API: Prepare Time Boundary\n```plain text\nPOST /mem-app/v4/credits/test/time-boundary\n```\n### What it does\nIt prepares a target record for a boundary and optionally runs the same production per-record worker immediately.\nSupported values:\n```plain text\nauthorization_expiry\npreview_cycle_end\npreview_cycle_renew\n```\n### When to use it\nUse this helper when the product behavior depends on time that QA cannot reasonably wait for:\n- expire an unused Before reservation without waiting for the full TTL;\n- verify that accepted usage is not incorrectly released by time;\n- end a `cancel_pending` Preview at its local cycle boundary;\n- renew an `active` Preview into its next monthly cycle, restoring Base Credits while preserving the current Credit Package;\n- test late Usage after authorization expiry.\nDo not use it to claim that Temporal itself fired on schedule. Automation Rules\n- Use a dedicated workspace per destructive balance/lifecycle test when possible.\n- Use unique IDs for each independent task and event.\n- Replay identical IDs only when testing idempotency.\n- Poll Get Test State instead of using a single fixed sleep.\n- Retry HTTP `503` and `429` with the same event IDs.\n- Do not retry HTTP `400` without fixing the payload.\n- Do not use `fresh=true` in a polling loop.\n- Do not mix helper-generated Version Tag ordering tests and real Version Tag Kafka tests on the same workspace.\n- Use a separate workspace for large balance-depletion tests so History assertions remain readable.\n- Do not depend on the old `force-activate` endpoint. Credits DLQ Record API\nReads credit-usage messages the consumer **refused before persistence**. These never reach `metronome_usage_logs`, so this archive is the only record of what upstream actually sent.\nSection 13 already surfaces these as `rejected_events`, with the Kafka coordinates and the rejection reason. Use this section when you need the **original payload**, or when you want to search the archive by something other than one user.\n### 14.1 Endpoints\n```javascript\nGET /membership/internal/credits/dlq/records       # list, without payload\nGET /membership/internal/credits/dlq/records/:id   # one record, with payload\n```\nThe split is deliberate. A rejected event's payload is user data, and a wide list query returning payloads would hand out hundreds of them at once. The bytes are reachable one row at a time, by an id you already have — either from a list response or from `rejected_events[].record_id` in section 13.\n### 14.2 Before You Start\nSame base URL and key as the other internal APIs in section 12.\n```bash\n# PRE\nBASE=http://plaud-membership-service-pre-usw2-lan.plaud.ai\n# Dev\n# BASE=http://plaud-membership-service-staging-usw2-lan.plaud.ai\n\nKEY=<internal API key>\n```\nThese are VPC-only hosts. Call them from the devbox, not from a laptop.\n### 14.3 List Parameters\nAll optional.
